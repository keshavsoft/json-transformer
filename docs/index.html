The Story & Philosophy

Why pure JSON transformation requires separating the Food from the Recipe: The journey from Source to Consumption.

1. The Central Invariant: From Source to Consumption

In modern software engineering, data must travel from external data producers to end-user applications. This creates a critical architectural boundary between three distinct worlds:

📡
1. Data Provider
Source JSON • The Food
Belongs to external systems (Tally ERP, SAP, SQL databases, XML exports). Sacred, verbose, and 100% immutable. You do not own it.
📜
2. Application
Transformation JSON • The Recipe
Belongs to your application contract. A clean, declarative recipe specifying which fields matter, what to rename, and how to nest.
🍽️
3. Consumer
Output JSON • Consumption
Belongs to the consumer (React/Vue UI, mobile clients, REST APIs). A pristine, predictable JSON schema ready for instant display or processing.
The Central Invariant: Source is data. Transformation is instruction. Output is result.
The transformation bridges differing shapes without side effects, without polluting upstream data, and without forcing compromises on the consumer.

2. What Happens When We Transfer from Source to Consumption?

Why do we need a transformation engine at all? Why can't developers just write a quick script or mutate the incoming payload directly?

Because that shortcut is where enterprise code goes to die. In real-world enterprise architectures, transferring data reveals three structural conflicts:

  • Cardinality Mismatches: Upstream systems (especially XML-based exports like Tally) output a plain object when there is one child element, but an array when there are multiple. Hand-written mapping scripts crash with TypeError: .map is not a function.
  • XML Artifact Pollution: Data comes wrapped in verbose nodes like #text, metadata like @_TYPE="String", and capitalized compound keys like BATCHALLOCATIONS.LIST. If passed raw to the consumer, the frontend UI becomes tightly coupled to ERP internal schemas.
  • Memory Leakage & Shared Mutability: When multiple concurrent requests mutate the incoming data in memory to reshape it, shared object references become corrupted, invalidating caches and triggering subtle race conditions.

@keshavsoft/json-transformer is the pure mediator. It performs a deterministic co-traversal: taking the food, following the recipe, and producing the transformed dish with zero mutations and zero side-effects.

3. Why Two Separate Files? The Immutability Principle

Developers sometimes ask: "Why maintain two separate JSON files? Why not embed transformation directives directly inside the source JSON?"

Embedding directives inside source data is a dangerous anti-pattern for three fundamental reasons:

  1. Client Data is Sacrosanct: You do not own the source data. Mutating incoming client payloads pollutes shared references, invalidates caches, and breaks downstream consumers.
  2. Preventing Infinite Loops: If the traversal engine were to mutate or enrich the source object while recursively navigating it, it would create self-referencing branches and trigger infinite loops.
  3. Different Lifecycles: Client data changes on every HTTP request or database query. The transformation recipe changes only when your business contract evolves. Decoupling them keeps your architecture rock-solid.

4. The Recipe is Knowledge, Not Duplication

Why does the recipe mirror the hierarchy of the source data? Because you cannot reliably reshape complex enterprise data without first proving you understand its hierarchy.

When an engineer constructs the recipe matching the path down to the target field, they formally prove:

  • Structural Proof: "I understand that STOCKITEM contains BATCHALLOCATIONS.LIST, which contains GODOWNNAME."
  • Intentionality: Only paths that are explicitly acknowledged and intended for transformation are altered. Everything else is safely pruned.
  • Protection from Sloppy Hacks: It prevents developers from taking lazy shortcuts or applying unvalidated transformations. The recipe is a disciplined blueprint of intent.

5. The KeshavSoft Declarative Ecosystem

This project is the transformation engine of a 3-part lossless declarative ecosystem:

The 3-Part Declarative Round-Trip:
  1. tag-to-json: Extracts live HTML DOM trees into declarative JSON specifications.
  2. json-transformer: Transforms heterogeneous domain data (APIs, Tally/XML, SQL) into canonical target data shapes or UI specs.
  3. json-to-tag: Renders declarative JSON specifications into reactive native HTML DOM elements.
