In real-time software development, we often execute a set of statements to perform a task. Most of the time, those statements are common and do a single job, so we naturally move them into a function.

A function starts clean and simple. It takes a minimal set of inputs, performs its operations, and returns a predictable result. For straightforward requirements, this pattern works reliably.

However, real-world requirements are rarely static. Soon, that same functionality needs to vary slightly based on different conditions, specific flags, or changing business rules. To handle these variations, we begin introducing parameters to the function.

At first, it is just one additional parameter. Then another. Then an optional options object. As the number of parameters increases, the complexity of the function compounds rapidly.

When a function accepts too many parameters, maintaining and testing it becomes extremely difficult. The function is no longer just executing its core task; it is now branching on flags, validating combinations of arguments, and guarding against undefined values.

As systems grow, inputs stop being simple values and start becoming complex data structures. At that point, passing a large object into a function stops being a good design.

In real applications, incoming payloads contain dozens or hundreds of fields: customers, orders, voucher lines, stock allocations, tax rules, and metadata. When developers pass this entire payload into a single function, the function is forced to act as a tree navigator, drilling into nested keys just to find the few values it actually needs.

This is where the story of json-transformer begins. Despite its name, the true thought process of this repository is not monolithic JSON transformation — it is JSON Traversal to run functions.

Instead of passing a massive structure into a function and forcing the function to navigate it, we invert the responsibility: we navigate the structure from the outside, and attach small, focused functions only where actions need to happen.

The data exists in a JSON tree. A declarative instructions recipe defines where actions should take place. The traversal engine walks the data from the outside, and when it reaches an instructed node, it runs the function with only the minimal, focused inputs that node needs.

The function stays small, the parameters stay minimal, and the traversal engine never has to change.
