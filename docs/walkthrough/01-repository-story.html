Document 1 — Repository Story Problem Statement

Why functions with large, complex inputs need structured tree navigation rather than monolithic parameter objects.
Functions work well when inputs are simple.
As systems grow, inputs stop being values and start becoming structures.
At that point, passing a large object into a function stops being a good design.

1. The Problem with Large Inputs

In small examples, a function usually looks like this: 

function processUser(user) {
  // do something with user
}

This works when user has a few obvious fields. But in real applications, inputs quickly grow into large objects:

  • customer information
  • order details
  • permissions and roles
  • billing addresses
  • system state
  • metadata

Developers often continue using the same pattern: 

function handleRequest(payload) {
  // payload contains dozens of properties and nested structures
}

The function becomes responsible for navigating the structure, checking which fields exist, deciding which parts matter, and extracting the values it needs.

2. Why This Becomes a Maintenance Burden

When a function receives a large input object:

  1. The function becomes tightly coupled to the input structure. If the structure changes, the function breaks.
  2. Navigation logic mixes with business logic. Code that exists only to drill down into objects clutters the core behavior.
  3. Testing becomes harder. To test one small rule, you must construct a large input object.
  4. Functions become difficult to reuse. Another part of the system cannot easily reuse the logic unless it provides the exact same payload shape.
Large Input Object → Function mixes traversal with logic → High coupling, brittle tests

3. Moving Navigation Out of the Function

Instead of passing the entire structure into the function and making the function navigate it, we can invert the responsibility:

Navigate the structure from the outside, and attach functions only where actions need to happen. 

Source Structure
      ↓
External Traversal
      ↓
Target Location Reached
      ↓
Small, Focused Function Executed

Now the function does not need to know where it lives in the larger system. It only receives the value it needs and does its job.

4. The Invariant: JSON Rules, External Code

To keep this predictable, we separate three concerns:

  • The source data: A plain JSON structure.
  • The instructions: Another JSON structure describing what should happen at specific locations.
  • The behavior: JavaScript functions supplied from outside.

The instructions describe where to act and what to do, but the actual implementation logic remains in external functions.

The Rule: JSON describes structure and instructions. JavaScript provides behavior. The traversal engine connects the two without mutating either.

5. The Result: A New In-Memory Object

When the system runs, it does not mutate the source data. Instead, it produces a new in-memory structure where functions are attached to the appropriate leaves.

Structure → Instructions → Traversal → In-Memory Function Tree

This allows an application to prepare a callable, structured representation of behavior that matches the shape of the source data.
