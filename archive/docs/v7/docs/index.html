The Story & Philosophy

Why functions with large, complex data need external tree traversal rather than monolithic parameter objects: The foundational thought process behind json-transformer.
Functions work well when inputs are simple.
As systems grow, inputs stop being values and start becoming structures.
At that point, passing a large object into a function stops being a good design.

1. The Origin: Functions and Their Inputs

In general, every function takes an input. In small examples, functions are clean, minimal, and focused: 

function processUser(user) {
  // do something simple with user
}

This works when inputs are minimal. But in real-world systems, the data an application deals with contains dozens or hundreds of fields:

  • Customer names, emails, phone numbers, and loyalty tiers
  • Order identifiers, dates, lines, vouchers, and statuses
  • Product codes, descriptions, stock batches, and price lists
  • Shipping addresses, tax configurations, and system metadata

Developers often continue passing the entire payload into a single function: 

function handleRequest(payload) {
  // payload contains dozens of properties and nested structures
}

When you do this, the function is forced to become a tree navigator. It has to inspect the structure, check which keys exist, guard against undefined properties, and drill down to extract values. The function's business logic gets buried underneath navigation boilerplate.

2. The Real Thought Process: Traversal Over Transformation

Although this repository is named json-transformer, the core thought process is not monolithic JSON transformation — it is JSON Traversal to run functions.

Instead of passing a massive structure into a function and forcing the function to navigate it, we invert the responsibility:

Navigate the structure from the outside, and attach functions only where actions need to happen.

Source Structure (JSON) → External Tree Traversal → Target Node Reached → Minimal Function Executed

Now the function does not need to know where it lives in the overall system. It does not need to know the entire schema. It receives only what it needs, executes its behavior, and exits.

3. The Three Independent Pillars

To keep this architecture completely predictable, testable, and reusable, we separate three distinct concerns:

🌲
1. The Source Data
JSON • Describes What Exists
Plain, immutable domain data (API payloads, ERP exports, database dumps). The source represents reality and is never mutated.
🧭
2. The Instructions
JSON • Describes Where to Act
Declarative recipe directives specifying which paths matter. Only targeted nodes have instructions; everything else is untouched.
⚡
3. External Functions
JavaScript • Supplies Behavior
Pure functions supplied from the outside. They know how to format, calculate, or log, but know nothing about the overall tree layout.
The Separation Rule:
JSON describes structure and instructions.
JavaScript provides behavior.
The engine connects the two without mutating the source or hard-coding paths inside functions.

4. The Leaf Function: Exactly Four Focused Inputs

When the traversal engine walks the source and reaches an instructed node, what does the external function receive? Rather than a massive, confusing payload, the engine supplies an envelope of exactly four arguments: 

function action(value, path, source, instruction) {
  // 1. What did we find here?
  console.log("Value:", value);

  // 2. Where are we in the tree?
  console.log("Path:", path);

  // 3. What is the complete context?
  console.log("Source:", source);

  // 4. Why was this function invoked here?
  console.log("Instruction:", instruction);
}

5. Structural Growth Without Algorithmic Changes

Because traversal is driven by the source, the engine code never needs to change when your data models scale:

  • Add a new root node (e.g. product) → Traversal discovers it and consults the recipe.
  • Nest deeper children (e.g. customer.email, product.code) → Traversal naturally continues downward.
  • Large source with sparse instructions → Traversal walks all nodes, but only executes functions at instructed locations.

The traversal logic remains identical whether your source contains two properties or ten thousand.
