The Developer Guide Core Engine Internals

Architectural specification for engine maintainers, contributors, and AI pair-programmers extending the src/v8/ compiler.

1. The Architectural Story: From v1 to v8

Transforming complex enterprise payloads (Tally XML, SAP IDocs, SQL hierarchies) often starts with imperative scripts full of nested for loops and mutable object modifications. In production, this approach collapses when encountering optional fields, mixed types, or multi-megabyte payloads.

Over eight successive major revisions (v1 through v8), @keshavsoft/json-transformer was distilled from experimental prototypes down to a minimal, mathematically pure specification compiler:

⚡ 1.2 KB Minified Footprint

The entire v8 engine compiles to just 1.29 KB of native ES module JavaScript with zero third-party dependencies.

🛡️ Pure Functional Invariant

(inSource, inRecipe) → Output JSON. No mutations, no external state, and no side-effects.

📁 Architecture as Structure

Zero inline comments. System architecture is conveyed completely by directory hierarchy and semantic naming.

🔒 Scoped Execution

Strict parameter envelope: inputs are unpacked immediately to immutable local... constants.

2. The Four Non-Negotiable Invariants

Before modifying any code in src/v8/, every engineer and AI agent must enforce these four principles:

Invariant 1: The in & local Parameter Convention

Every function in the engine accepts a single configuration object with in-prefixed keys, and immediately assigns each key to a local-prefixed constant:

// CORRECT — Adheres to KeshavSoft convention
const startFunc = ({ inSource, inRecipe }) => {
    const localSource = inSource;
    const localRecipe = inRecipe;

    // Only localSource and localRecipe are referenced below
    if (Array.isArray(localSource)) {
        return traverseArray({ inItems: localSource, inRecipe: localRecipe });
    }
    ...
};

// VIOLATION — Never use naked positional arguments
function startFunc(source, recipe) { ... }

Why this rule matters: It eliminates parameter re-assignment bugs, guarantees parameter immutability, and establishes consistent stack traces across every module.

Invariant 2: Absolute Source Immutability

inSource belongs to the external data provider. It must never be mutated, altered, or augmented in place. The transformed result is constructed fresh as a new object or array. This guarantees that caches, parent references, and upstream callers remain uncorrupted.

Invariant 3: Zero Runtime Dependencies

The engine uses pure ECMAScript. No lodash, no ramda, no helper libraries. This guarantees zero supply-chain vulnerabilities, instant load times in browser runtimes, and frictionless integration into edge runtimes (Cloudflare Workers, Deno, Bun).

Invariant 4: Zero Code Comments in Core Code

Code intent is expressed through modular directory organization and explicit function names. If a function requires an inline comment to explain what it does, it is refactored into a named submodule instead.

3. The Traversal Pipeline Anatomy

The v8 engine consists of five targeted modules working in synchronized harmony:

src/v8/index.js Public API Envelope
Acts as the consumer-facing boundary. Converts positional arguments (source, recipe) into the internal { inSource, inRecipe } configuration object and invokes the central dispatcher. 
import traverse from "./traverse.js";

const transform = (source, recipe) => {
    const localSource = source;
    const localRecipe = recipe;

    return traverse({
        inSource: localSource,
        inRecipe: localRecipe
    });
};

export default transform;
src/v8/traverse.js Central Dispatcher
The core traffic controller. It inspects the runtime data type of localSource:
  • Arrays branch immediately to traverseArray.
  • Objects branch to traverseObject.
  • Primitives (strings, numbers, booleans, null) pass through unchanged.
const startFunc = ({ inSource, inRecipe }) => {
    const localSource = inSource;
    const localRecipe = inRecipe;

    if (Array.isArray(localSource)) {
        return traverseArray({ inItems: localSource, inRecipe: localRecipe });
    }

    if (typeof localSource === "object" && localSource !== null) {
        return traverseObject({ inSource: localSource, inRecipe: localRecipe });
    }

    return localSource;
};
src/v8/traverseObject/index.js The Secret Gatekeeper
The architectural turning point: How does the engine know whether to reshape an object? It checks the Recipe, not the source! If "transform" in localRecipe is true, it enters reshaping mode via ifTransformFound. If absent, child properties continue their traversal unhindered, preventing data loss. 
let newElement = localSource;

if (localRecipe && typeof localRecipe === "object" && "transform" in localRecipe) {
    newElement = ifTransformFound({
        inSource: localSource,
        inTransform: localRecipe.transform
    });
}

for (const [key, value] of Object.entries(newElement)) {
    if (Array.isArray(value) && localRecipe && key in localRecipe) {
        newElement[key] = traverseArray({ inItems: value, inRecipe: localRecipe[key] });
    }
}

return newElement;
src/v8/ifTransformFound/index.js The Inversion of Control
A brilliant role inversion: localSource drives the iteration (no phantom properties created), while localTransform acts as the directive lookup. Keys absent from the recipe are pruned automatically. 
for (const [key, value] of Object.entries(localSource)) {
    if (!(key in localTransform)) {
        continue; // Unacknowledged properties are pruned
    }

    const directive = localTransform[key];
    const newKey = directive?.alterKey || key;
    let processedValue = value;

    if ("transform" in directive) {
        processedValue = traverse({ inSource: value, inRecipe: directive });
    }

    if (directive?.valueType === "array" && !Array.isArray(processedValue)) {
        processedValue = [processedValue];
    }

    if (directive?.valueKey && processedValue && typeof processedValue === "object") {
        processedValue = processedValue[directive.valueKey];
    }

    newElement[newKey] = processedValue;
}
src/v8/traverseArray/index.js Collection Processor
Maps every array element recursively through traverse, flattens deep sub-arrays with .flat(Infinity), and strips empty/falsy residues with .filter(Boolean). 
const startFunc = ({ inItems, inRecipe }) => {
    const localItems = inItems;
    const localRecipe = inRecipe;

    return localItems
        .map((item) => traverse({ inSource: item, inRecipe: localRecipe }))
        .flat(Infinity)
        .filter(Boolean);
};

4. Execution Trace Walkthrough

Here is what happens inside the engine when processing a Tally stock item:

1. transform(food, recipe)
→ Enters traverse({ inSource, inRecipe })
→ Type is Object: Enters traverseObject
→ Recipe has "transform": Enters ifTransformFound
• Matches key "STOCKITEM" → has nested "transform"
• Recurses to traverse({ inSource: STOCKITEM, inRecipe: directive })
→ Type is Array: Enters traverseArray
• Maps item #0 → traverse({ inSource: item[0], inRecipe })
• Applies alterKey: "Name" → outputs clean name
• Applies valueKey: "#text" to BASEUNITS → extracts "kgs"
• Applies valueType: "array" to BATCHALLOCATIONS.LIST → returns clean array
← Returns mapped & filtered array
← Constructs new root object
← Returns final reshaped JSON output

5. Enterprise XML & Tally Quirks Handled by Design

The architecture inherently neutralizes real-world enterprise edge cases:

  • Literal Dotted Keys: Tally exports often contain literal dots in property names, such as BATCHALLOCATIONS.LIST or LEDGERNAME.#text. Because ifTransformFound uses direct property indexing (localTransform[key]), literal dotted keys match without ambiguous path splitting.
  • Single-Item Object / Array Inconsistency: XML parsers turn multiple child tags into an Array, but a single child tag into a plain Object. The valueType: "array" directive guarantees downstream consistency regardless of incoming cardinality.
  • Deep Tree Cleanliness: Unwanted metadata attributes (e.g. @_TYPE="String", @_RESERVEDNAME="") are naturally pruned because they are never listed in the recipe.

6. Engine Development & Test Workflow

When developing or validating engine modifications, use the containerized test suite:

1. Run Real-World Enterprise Samples (Zero-dependency test)

# Inside container or via wslc:
wslc exec node-dev node samples/6oct/batches/index.js

# Or test the simple sample:
wslc exec node-dev node samples/new/simple/index.js

2. Build the Production Bundle

wslc exec node-dev npm --prefix /workspace/json-transformer run build

This generates the production bundle at docs/dist/v8/min.js and copies it to docs/dist/min.js.
