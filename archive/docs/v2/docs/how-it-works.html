How It Works

The architectural epic: How two decoupled objects coordinate to transform enterprise data with zero side effects.

1. The Big Picture: Two Objects in Perfect Harmony

Conventional developers often ask: "Why do I need two objects? Why can't I just write a quick script or mutate the incoming payload directly?"

Because that shortcut is where enterprise code goes to die. In real-world software, data and business rules have completely different lifecycles:

  • inSource (The Food): The raw, sacred incoming payload from external systems (Tally XML, SAP, SQL). You do not own it. Mutating it causes memory leaks, corrupts shared references, and breaks downstream consumers.
  • inRecipe (The Instruction): The declarative contract representing your domain knowledge. It defines which keys matter, how they should be renamed, and what types they must become.

The transformation engine is the pure mediator. It traverses both objects in tandem, using the recipe as the blueprint and the source as the fuel, producing a pristine new object tree.

2. The Core Dispatcher: traverse.js

When you call transform(source, recipe), the engine routes the input through a single, elegant dispatcher:

const startFunc = ({ inSource, inRecipe }) => {
    const localSource = inSource;
    const localRecipe = inRecipe;

    if (Array.isArray(localSource)) {
        return traverseArray({ inSource: localSource, inRecipe: localRecipe });
    }

    if (localSource && typeof localSource === "object") {
        return traverseObject({ inSource: localSource, inRecipe: localRecipe });
    }

    return localSource;
};

Notice the discipline: primitives (strings, numbers, booleans) pass straight through. Arrays branch to array-handling. Objects branch to object-handling. There are no magical fallbacks, no defensive type guessing, and no hidden state.

3. The Secret of Line 14: The Recipe is the Gatekeeper

When the dispatcher enters traverseObject, how does it know whether to reshape the object or preserve its shape? It inspects the Recipe, not the source:

if (localRecipe && typeof localRecipe === "object" && "transform" in localRecipe) {
    newElement = ifTransformFound({
        inSource: localSource,
        inTransform: localRecipe.transform
    });
}

This is the fundamental turning point:

  1. The Recipe Grants Permission: The engine does not guess or assume. Only if the recipe explicitly contains the "transform" directive does the engine enter reshaping mode.
  2. Domain Proof: The presence of "transform" is proof that the engineer explicitly intended to transform this specific layer of the tree.
  3. Pass-Through Safety: If "transform" is absent, child properties continue their traversal unhindered, preventing data loss in deeply nested enterprise trees.

4. The Inversion of Control: Source Becomes the Driver

Once the engine verifies that "transform" is present, it calls ifTransformFound. Here, a brilliant role inversion occurs:

for (const [key, value] of Object.entries(localSource)) {
    if (!(key in localTransform)) {
        continue;
    }

    const directive = localTransform[key];
    const newKey = directive?.alterKey || key;
    // apply valueType, valueKey, and recursive transform...
}
The Two Roles:
  • localSource drives the iteration: The actual data present in the client payload determines what gets processed. The engine never invents phantom properties.
  • localTransform acts as the lookup filter: If a key exists in the source but is absent from the recipe, it is pruned immediately. Only explicitly acknowledged fields survive.

This role inversion gives you the best of both worlds: strict schema security (only desired fields pass) combined with runtime dynamic flexibility (only fields actually present in the payload are output).

5. Deep Recursive Descent

Enterprise payloads are rarely flat. A Tally sales voucher contains inventory entries, which contain batch allocations, which contain godown names. How does the engine navigate this without losing context?

When a directive contains a nested transform, ifTransformFound recurses right back into the central dispatcher:

if (directive && typeof directive === "object" && "transform" in directive) {
    transformedValue = traverse({
        inSource: value,
        inRecipe: directive
    });
}

Because every step goes through traverse, the engine handles arbitrary depth and any combination of nested objects and arrays without maintaining any global mutable stack.

6. Array Dynamics: traverseArray

Arrays in business payloads often contain empty strings, null items, or repetitive rows. traverseArray maps each item through the dispatcher and prunes empty residue:

const startFunc = ({ inSource, inRecipe }) => {
    const localSource = inSource;
    const localRecipe = inRecipe;

    return localSource
        .map(item => traverse({ inSource: item, inRecipe: localRecipe }))
        .filter(item => item !== null && item !== undefined);
};

If the array item is an object, it gets transformed according to the recipe. If the array has only a single element and the recipe specifies unwrapping, it normalizes cleanly.

7. Architectural Purity

Every file in the src/v8/ engine adheres to the strict KeshavSoft Engineering Principles:

  • Single Responsibility: One folder, one function, one purpose.
  • In-Local Variable Isolation: Every function strictly accepts { in... } parameters and assigns them to immutable local... constants.
  • Zero Code Comments: Code communicates its intent purely through clean directory names, file names, and declarative structure.
  • Zero Dependencies: Completely native ES modules with zero third-party packages or runtime overhead.
